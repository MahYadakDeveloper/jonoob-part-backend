# یادداشت: لایه‌ی اعلان ابطال cache (Invalidation Hint)

یادداشت نکات کلیدی برای قرارداد اعلان ابطال بین API و کلاینت‌ها، به‌عنوان لایه‌ی دوم در معماری cache محصولات.

---

## ۱. جایگاه این لایه

معماری cache سه لایه دارد و هر لایه مستقل از دیگری کار می‌کند:

| لایه | نقش |
|---|---|
| ۱. HTTP caching | پایه؛ ETag، TTL کوتاه و stale-while-revalidate. بدون هیچ push، داده بعد از TTL اصلاح می‌شود |
| **۲. اعلان ابطال (این سند)** | بهینه‌سازی؛ کلاینت را سریع‌تر از TTL مطلع می‌کند که داده‌اش کهنه شده |
| ۳. changes feed | جبران؛ پیام‌های از دست رفته را بعد از قطع اتصال بازیابی می‌کند |

نتیجه: اگر لایه‌ی اعلان خراب باشد یا پیامی گم شود، سیستم نمی‌شکند، فقط تازگی داده کمی دیرتر می‌رسد.

---

## ۲. اصل اول: hint بفرستید، نه داده

پیام ابطال فقط می‌گوید **چه چیزی تغییر کرده**، نه مقدار جدید آن را. کلاینت داده‌ی تازه را از همان GET معمولی می‌گیرد.

دلایل:
- پیام کوچک می‌ماند و حجم کانال کم است.
- داده از مسیر عادی (با همه‌ی قواعد دسترسی و cache) می‌آید؛ منطق دسترسی در کانال push تکرار نمی‌شود.
- داده‌ی خصوصی یا حساس از کانال اعلان عبور نمی‌کند.
- یک منبع حقیقت برای محتوا وجود دارد: endpoint خود منبع.

---

## ۳. محتوای پیام

| فیلد | توضیح |
|---|---|
| نوع پیام | ثابت: ابطال |
| نوع منبع | مثلاً محصول، دسته |
| شناسه‌ی منبع | شناسه‌ی عمومی (نه شناسه‌ی داخلی دیتابیس) |
| نسخه (`version`) | عدد صعودی منبع؛ مبنای مقایسه |
| نشانگر (`cursor`) | موقعیت پیام در changes feed؛ برای هماهنگی با لایه‌ی ۳ |
| برچسب (`tag`) | اختیاری؛ برای ابطال گروهی (مثلاً دسته یا لیست) |

نکته: پیام را عمداً کم‌فیلد نگه دارید تا قرارداد پایدار بماند.

---

## ۴. قواعد پردازش در کلاینت

- اگر نسخه‌ی پیام **کمتر یا مساوی** نسخه‌ی cache بود، پیام نادیده گرفته می‌شود. این قاعده تکرار و خارج از ترتیب بودن پیام را بی‌اثر می‌کند.
- اگر نسخه‌ی پیام **بیشتر** بود، cache آن منبع کهنه علامت می‌خورد و دوباره‌گرفتن انجام می‌شود (فوری یا هنگام نیاز بعدی، بسته به اهمیت داده).
- پیامی که کلاینت منبعش را در cache ندارد، نادیده گرفته می‌شود.
- دوباره‌گرفتن‌ها باید **تجمیع شوند**؛ چند پیام پشت سر هم برای یک منبع نباید چند درخواست بسازد.
- پیام ابطال هرگز مستقیم داده را بازنویسی نکند.

---

## ۵. لیست‌ها و ابطال گروهی

ابطال تک‌تک محصول برای لیست‌ها (دسته، جستجو، فیلتر) کافی نیست، چون نمی‌دانید کدام لیست‌ها آن محصول را شامل می‌شوند.

- از **tag یا نسخه‌ی مجموعه** استفاده کنید (مثلاً برای هر دسته یک نسخه).
- تغییر یک محصول، علاوه بر نسخه‌ی خودش، نسخه‌ی tagهای مرتبط را هم بالا می‌برد.
- کلاینت لیست cache‌شده را با tag آن مرتبط می‌کند و با پیام tag، آن لیست را کهنه علامت می‌زند.
- از ابطال همه‌چیز (full flush) برای هر تغییر پرهیز کنید؛ cache بی‌فایده می‌شود.

---

## ۶. جریان سمت سرور

```
دامنه (catalog) ─▶ outbox ─▶ worker ─▶ نگاشت به قرارداد عمومی ─▶ کانال تحویل
```

نکات مهم:
- **رویداد داخلی دامنه با قرارداد عمومی کلاینت یکی نباشد.** worker (یا یک لایه‌ی اعلان کلاینت) رویداد داخلی را به پیام عمومی نگاشت می‌کند. وگرنه هر refactor داخلی، قرارداد کلاینت‌ها را می‌شکند.
- **outbox در همان تراکنش تغییر داده نوشته شود** تا تغییر بدون اعلان یا اعلان بدون تغییر پیش نیاید.
- **تحویل at-least-once است**؛ پس پیام باید idempotent باشد. نسخه این را تضمین می‌کند.
- **ترتیب تضمین نمی‌شود**؛ مقایسه‌ی نسخه در کلاینت آن را جبران می‌کند.
- **تجمیع (coalescing)**: اگر یک منبع در بازه‌ی کوتاه چند بار تغییر کرد، فقط پیام آخرین نسخه ارسال شود.
- **نگاشت و ارسال در worker** انجام شود، نه در مسیر درخواست کاربر؛ تأخیر اعلان نباید روی تجربه‌ی نوشتن اثر بگذارد.

---

## ۷. انتخاب کانال تحویل

قرارداد پیام یکی است؛ کانال جزئیات قابل تعویض است.

| کانال | مناسب برای | نکته |
|---|---|---|
| SSE | وب، پنل مدیریت، POS | ساده، یک‌طرفه، reconnect داخلی؛ برای اعلان معمولاً بهترین گزینه |
| WebSocket | وقتی کانال دوطرفه هم لازم است | پیچیده‌تر (heartbeat، reconnect، احراز هویت) |
| Push موبایل | اپ در پس‌زمینه | غیرقابل اتکا از نظر زمان؛ فقط به‌عنوان hint |
| Webhook | سیستم‌های بیرونی و شرکا | امضا، retry و idempotency لازم است |
| پاک‌سازی CDN | cache لبه‌ای | با کلیدهای surrogate/tag؛ ابطال در لایه‌ی HTTP |

---

## ۸. امنیت و دسترسی

- دسترسی به اشتراک (subscription) هنگام اتصال بررسی شود و فقط منابع مجاز برای آن کلاینت اعلام شود.
- پیام حاوی داده‌ی خصوصی، قیمت اختصاصی یا اطلاعات گروه مشتری نباشد. اگر قیمت برای هر گروه فرق می‌کند، پیام فقط می‌گوید «محصول تغییر کرد» و کلاینت با دسترسی خودش داده را می‌گیرد.
- webhook با امضا و timestamp تأیید شود.
- نرخ ارسال به هر اتصال محدود شود تا تغییرات انبوه (مثلاً به‌روزرسانی قیمت همه‌ی کالاها) کلاینت‌ها را غرق نکند. برای تغییر انبوه، یک پیام ابطال کلی (مثلاً برای کل کاتالوگ) بهتر از هزاران پیام تکی است.

---

## ۹. قرارداد و نسخه‌گذاری

- قرارداد پیام با **JSON Schema یا AsyncAPI** تعریف شود و منبع حقیقت باشد، نه مستندات جانبی.
- در یک پکیج جدا (مثلاً `contracts`) نگهداری شود تا `apps/*` و SDK کلاینت هر دو از آن استفاده کنند، نه از impl دامنه.
- تغییرات فقط **افزایشی** باشد (فیلد اختیاری جدید) تا کلاینت‌های قدیمی نشکنند.
- کلاینت باید **فیلد ناشناخته را نادیده بگیرد**.

---

## ۱۰. خطاها و رفتار در شرایط بد

| وضعیت | رفتار |
|---|---|
| قطع اتصال | reconnect با backoff؛ بعد از اتصال، هماهنگی با changes feed (لایه‌ی ۳) |
| پیام تکراری | نادیده گرفته می‌شود (مقایسه‌ی نسخه) |
| پیام خارج از ترتیب | نسخه‌ی کمتر نادیده گرفته می‌شود |
| پیام گم‌شده | حداکثر تا TTL لایه‌ی ۱ یا تا بازیابی از changes feed |
| خرابی worker | outbox پیام‌ها را نگه می‌دارد و بعد از بازگشت ارسال می‌شود |
| تغییر انبوه | پیام ابطال کلی به‌جای ارسال تکی |

## ۱۱. چک‌لیست تصمیم‌ها

- [ ] پیام فقط hint باشد، بدون داده
- [ ] هر منبع نسخه‌ی صعودی دارد
- [ ] کلاینت پیام با نسخه‌ی کمتر یا مساوی را نادیده می‌گیرد
- [ ] ابطال لیست‌ها با tag یا نسخه‌ی مجموعه انجام می‌شود
- [ ] رویداد داخلی به قرارداد عمومی نگاشت می‌شود
- [ ] outbox در همان تراکنش تغییر نوشته می‌شود
- [ ] ارسال در worker و با تجمیع پیام‌ها
- [ ] کانال تحویل قابل تعویض است
- [ ] پیام حاوی داده‌ی خصوصی نیست
- [ ] تغییر انبوه پیام کلی دارد
- [ ] قرارداد پیام در پکیج مستقل و فقط افزایشی نسخه‌گذاری می‌شود
